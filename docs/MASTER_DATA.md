# Master Data: schema, queries and checks

The staff-only Master Data page manages `items`, `units`, `purchaseTypes`, `users` and `settings`. Staff means an active `admin` or `account_admin` profile. No master record is hard-coded. Permanent client deletes are denied; deactivation sets `active: false` and preserves references.

## Storage contract

- `items/{autoId}`: `itemCode` (uppercase, unique, immutable), `name`, `description`, `defaultSellingPrice` (rupees, nonnegative), `defaultUnitId`, `active`, `createdAt`, `createdBy`, `updatedAt`.
- `units/{autoId}`: `name`, `symbol`, `active`, `createdAt`, `updatedAt`.
- `purchaseTypes/{autoId}`: `name`, `description`, `active`, `createdAt`, `updatedAt`.
- `users/{Auth UID}`: `displayName`, `role`, `active`, `createdAt`, `updatedAt` for profiles created in this screen. Profiles created in Firebase Console may lack timestamps; subsequent edits add `updatedAt`.
- `settings/{autoId}`: `key` (immutable), `value`, `description`, `active`, `createdAt`, `updatedAt`. Store non-secret text only.
- `itemCodes/{itemCode}` is an internal reservation document containing `itemId` and `createdAt`. Item creation writes the item and reservation in one Firestore transaction. Rules cross-check both documents with `getAfter()`; a reserved code cannot be reused, even after deactivation.

Item document IDs are generated by Firestore and stay stable when names change. User profile IDs are Firebase Auth UIDs, never names. Item codes cannot be edited after creation; create a replacement item and deactivate the old one if a code must change. Before importing existing item records, backfill and verify the `itemCodes` registry using a trusted administrative process so uniqueness remains complete.

Future order, purchase and invoice lines must store item name, code, unit name/symbol, quantity and price **snapshots** alongside the item and unit IDs. Historical documents must not render mutable master values as their source of truth.

## Query and index inventory

| Query | Used by | Composite index |
|---|---|---|
| `getDocs(collection(db, type))` for each of the five collections | Master table | None; collection scan |
| `getDocs(collection(db, 'units'))` | Item list labels and item form | None; collection scan |
| `getDoc(units/{id})`, `getDoc(users/{uid})`, and master record `getDoc` | Validation and edit/deactivation | None; document reads |
| `transaction.get(itemCodes/{code})` and `transaction.get(units/{id})` | Unique item creation | None; document reads |

Search, active filtering, sorting and ten-row pagination run on the retrieved collection in the browser. They apply to the **whole loaded collection**, not merely one page. No composite index is required for these queries. This is suitable for a modest catalogue; it reads every document each time a tab or Refresh loads. For larger collections, replace it with server-side cursor queries and document the resulting indexes before release. Firebase's [index overview](https://firebase.google.com/docs/firestore/query-data/index-overview) explains automatic and composite indexes.

## Manual checks before use

Use the Firestore emulator or Console Rules Playground with the exact local `firestore.rules`, and use client SDK identities for direct-access tests. Privileged Console Data/Admin SDK writes bypass rules.

1. As Admin, add active unit, purchase type, setting and item. Confirm server timestamps and generated IDs. As Account Admin, repeat. As User and signed-out client, attempt direct creates/updates/deletes of every collection: all must fail.
2. Try blank names, negative and fractional-cent prices, missing/inactive unit IDs, invalid item codes, duplicate codes, and concurrent same-code creates. All must fail. Confirm item code remains immutable through direct updates.
3. Edit and deactivate every master type, then reactivate via Edit. Confirm permanent deletes fail. Deactivate a unit referenced by an item; the item remains intact. Changing an item's unit must require an active target unit.
4. Create an Auth account in Firebase Console, then create its profile from the Users tab using the exact UID. Verify Account Admin can create/edit User profiles only; only Admin can assign staff roles. Neither staff account can change its own profile through the client. User direct profile writes must fail.
5. Switch tabs, search, filter, sort and paginate with more than ten records. Confirm empty and error states. Revoke a signed-in staff profile and confirm the visible workspace closes; direct master reads/writes must then fail.
6. Verify item creation fails if either the item or its code reservation is written alone, and that deleting a referenced item/unit is denied. No workflow or test should put credentials in `settings` or `users`.

The repository now has emulator configuration and automated rules tests. Use `npm.cmd run test:rules` locally; the tests load the exact `firestore.rules`. Keep the business-write boundary in `docs/FIRESTORE_SCHEMA.md` in place while operational workflows are designed.
