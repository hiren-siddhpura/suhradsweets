# Order lifecycle and local testing

New orders are saved as Confirmed in one trusted transaction. That transaction checks active products, units, prices and available stock, deducts the required stock once, writes immutable stock movements and snapshots, and records both creation and confirmation audit events. The inventory model does not support reservations: `reservedQty` must remain zero. Transactional stock deduction at confirmation prevents competing orders from overselling. Historical Draft orders remain Draft until an authorized user explicitly confirms them; invoice creation does not confirm a Draft. Admin may edit a Confirmed order before its invoice exists. Legacy Draft edits remain available to authorized owners and staff. A Confirmed edit reconciles the stock difference in the same transaction. Archive is a soft flag and leaves status, stock and reporting intact.

The new-order customer selector searches permitted customers by name or phone and provides a separate **Add New Customer** action. The shared customer dialog preserves entered lines, dates and notes. Staff can create the customer through the existing permission-checked customer transaction and select its real document ID immediately. For an ordinary User, customer details remain pending until the trusted order transaction creates the customer and confirmed order together. Existing contact reservations and ownership checks remain in force.

An invoice document or any payment history blocks edits in the trusted backend. A legacy `paymentRequestedAt` blocks archive/restore. The pre-invoice **Record payment request** operation does not send a message, collect payment, create an invoice or count any amount as received. Invoice creation and payment request both read the order in a transaction, so concurrent edits or archive attempts retry against the updated state. Payment submission continues to require an invoice. These operations need deployed trusted Functions for live use; the browser cannot write order or inventory documents directly.

The Orders screen no longer offers the pre-invoice **Record payment request** button, because it does not create a financial record and was easily mistaken for the invoice payment action. Existing `paymentRequestedAt` orders and the trusted operation remain compatible. An authorized Admin, Account Admin or assigned User creates an invoice from a Confirmed order; the owner then uses **Add payment** on that invoice.

An eligible archived order may be cancelled without restoring it first. Cancellation keeps `archivedAt` and the archive audit event, marks status `cancelled`, and atomically records the actor, reason, time and inventory adjustment. Confirmed stock deductions are restored once; a legacy order with an explicit `stockReservations` snapshot releases those reservations without increasing on-hand stock; a Draft with no stock movement changes no inventory. The current order-creation flow does not create reservations, and ordinary inventory operations still reject nonzero `reservedQty`. A missing or ambiguous stock snapshot requires review. Invoice records, invoice lock fields, payment history, and payment requests continue to block ordinary cancellation.

Admin, Account Admin and an assigned User may invoice an eligible Confirmed order. Invoice creation uses the existing order number and price snapshots, creates the invoice at the deterministic order ID, writes `order.invoice_created` and `order.locked` audit events, and sets the order's invoice lock fields in one transaction. It does not change stock. A retry cannot create another invoice. A pre-invoice request records `order.payment_requested` separately. The invoice starts `unpaid`. From the invoice, **Add payment** submits an unverified cash, UPI or bank-transfer payment and changes the invoice to `in_process`; another submission is blocked until review. Only verification increases the invoice's verified aggregate. A rejected payment restores `unpaid` or `partial`, and a verified partial payment permits a later submission for the balance. Admin and Account Admin can review submissions; verification of the full balance marks the invoice paid in the same transaction. An unverified payment mode can be corrected with a reason and a matching immutable audit event. Verified payments require reversal.

The Orders screen shows all accessible orders by default, including archived history. The archive filter narrows the view without removing records from reports. The order editor shows stock from a restricted callable: `available = onHandQty - reservedQty`; current policy keeps reservedQty at zero. An unavailable reading is shown as unknown. The UI warns about insufficient stock, while order creation, legacy Draft confirmation and confirmed-order edits validate against current inventory in a backend transaction. Special-product stock comes from its component items.

New successful order activity events are written atomically to existing `auditLogs`. They include server timestamp, authenticated actor UID/name snapshot, order/customer identifiers and name snapshots, outcome, reason where supplied and field-level changes where applicable. Failed transactions do not create success events. The activity UI reads these records directly from Firestore. User queries include `ownerUid == authenticated UID`, and Firestore Rules enforce that boundary; staff may view all. Older audit events without `ownerUid` remain in Firestore but cannot be shown to a User. Legacy payments without name snapshots use a restricted batch name resolver; missing profiles display `Unknown user`. UIDs remain the permanent reference.

The order activity queries require the two `auditLogs` composite indexes in `firestore.indexes.json`: `referenceType ASC, at DESC` and `referenceType ASC, ownerUid ASC, at DESC`. They have only been prepared locally; no index or Rules were published. Search filters are applied to server-scoped pages and exported across the authorized filtered result set. With very sparse search matches, an export can require many page requests; retain operational filters and monitor scale before using this as a bulk archive facility.

## Local checks

From PowerShell in the project root, run:

```powershell
npm.cmd run test:unit
npm.cmd run test:orders
npm.cmd run test:finance
npm.cmd run test:rules
```

The emulator commands require Java 21 and Firebase CLI. Follow `README.md` for emulator setup and local app mode. Use only emulator accounts for these checks. In the Orders page, create an order and verify its Confirmed status, stock movement and activity log. Admin can edit its quantity before invoice creation. Then create an invoice and verify that editing is locked and stock was not deducted again. No production data or deployment is needed for local tests.
