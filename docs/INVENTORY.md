# Inventory controls

The Inventory page shows balances for staff and permitted order movement history for ordinary Users. Staff cards count actual item documents. Stock status is calculated from `inventory/{itemId}` and the item master record in this order: **Blocked** (selling blocked or item deactivated), **Out of stock** (available quantity is zero), **Low stock** (positive configured threshold reached), **Available**. Available quantity is on hand minus reserved; the current backend requires reserved quantity to remain zero. Deactivated items must be reactivated in Master Data before they can be sold.

Physical stock count is an **absolute** quantity. The UI sends the count, a mandatory reason, an operation ID reused on retry, and the on-hand quantity seen when the dialog opened. The trusted `adjustStockCall` reads the current inventory record in a transaction. It rejects a stale count, validates bounds, writes the new balance, creates one signed `inventoryMovements` record and creates an immutable audit event. A repeated operation ID with the same payload returns the prior result without a second movement. Blocking/unblocking and threshold changes use `setInventoryControlCall`; they preserve quantity, require a reason in the backend, and record before/after control values with the authenticated actor UID, actor-name snapshot and server timestamp. The UI requires an explicit block reason; unblock and threshold actions use clear fixed reasons. Stale control dialogs are rejected when the previous block state or threshold changed.

New movements include an actor-name snapshot. Historical movements without it display `Unknown user`, while retaining the actor UID in Firestore. Stock history uses the existing movement collection; blocking actions are recorded in `auditLogs` because they have no quantity movement. Purchases remain independent of inventory. Blocking stops new order confirmation and any confirmed-order edit that needs **additional** blocked stock. It does not rewrite an already confirmed order, remove its stock deduction, or prevent its authorized fulfilment/cancellation workflow.

Run `npm.cmd run test:unit`, `npm.cmd run test:operations`, `npm.cmd run test:orders`, and `npm.cmd run test:rules` from PowerShell with Java 21 and Firebase CLI available. If the default emulator port 8080 is occupied, run the suites with a temporary Firebase config using an unused Firestore port; do not publish the config. The live stock actions still require the trusted callable backend to be deployed on a Firebase plan that supports Cloud Functions. No deployment or production migration is performed by these local changes.
