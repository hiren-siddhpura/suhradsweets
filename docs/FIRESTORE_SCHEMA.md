# Firestore schema and trust boundary

This is the contract for the required 17 top-level collections. Purchase, inventory, customer, order and financial operations are implemented locally through trusted callable functions. They require deployment before live use. All IDs are stable Firestore document IDs; monetary transaction values are integer **paise**, and stock quantities are integer **milli-units** (1,000 milli-units = one item's default unit). Every timestamp is a Firestore server timestamp. Do not store passwords, Auth tokens, service-account material or Google Drive file contents in Firestore.

`stockOperations/{operationId}` is an **internal** idempotency collection for physical adjustments; only the trusted backend writes it. `itemCodes/{itemCode}` is an **internal** reservation collection, outside the 17 business collections. Item creation atomically writes `items/{autoId}` and `itemCodes/{itemCode}`. The code reservation is never reused, including after deactivation.

`customerContacts/{sha256(normalizedContact)}` reserves an exact normalized contact across customers; staff client transactions may create/release reservations only alongside matching customer changes. `orderCounters/{year}` allocates sequential order numbers. `orderControls/global` stores `acceptingOrders`, `updatedBy` and `updatedAt`; active profiles may read it, and only trusted staff operations write it. Browser writes to the counter and global order controls remain denied.

## Operation invariants for the trusted backend

1. **Draft order:** no inventory movement. Fixed order unit IDs are `kg`, `500gm` and `250gm`; only Admin sees and can select `250gm`. The backend reads the matching item price (`defaultSellingPrice`, `sellingPrice500Gm`, or `sellingPrice250Gm`) and snapshots it on the line. A missing size price rejects the order. Existing item default units still govern stock quantities; unit selection does not convert stock. Older lines and invoices retain their saved unit and price snapshots.
2. **Confirm order:** verify Auth identity and active role, read the draft and current item/component inventory in a Firestore transaction, recompute required quantities and totals, reject insufficient stock, change status to `confirmed`, decrement each balance, append deterministic movement IDs and an audit event. Reject a second confirmation; transaction retries must not repeat the deduction.
3. **Confirm purchase:** draft-to-confirmed changes the purchase status and audit only. Purchase creation, editing, confirmation and cancellation never mutate inventory. Historical lines/movements are retained.
4. **Cancel confirmed order:** where policy allows, transition once to `cancelled`, restore exactly the original confirmed component quantities (from protected snapshots), append reverse movements and audit. A draft cancellation does not restore stock. Define restrictions for already invoiced/fulfilled orders before enabling cancellation.
5. **Special products:** staff configure final price and component recipe; confirmation uses the stored final price and deducts each component. A later recipe or price change never rewrites prior order snapshots.
6. **Create invoice:** explicit staff action only for a confirmed order; derive immutable lines and total from its confirmed snapshot, ensure one active invoice per order, and append an audit event.
7. **Submit/review payment:** validate cash, UPI or bank transfer, positive amount, invoice/order ownership and online reference uniqueness in a transaction. A submission starts `unverified` and atomically sets the invoice to `in_process`. A second submission is blocked while an unverified payment exists. Only staff verification contributes to `verifiedPaidPaise`; rejection returns the invoice to `unpaid` or `partial` as appropriate. Partial verification permits a later submission for the remaining balance. `ready_to_mark_paid` means fully verified but not yet marked paid. Review/rejection append audit events. One explicit reversal record per verified payment reduces the aggregate without deleting payment history.
8. **Mark as Paid:** an authenticated **Account Admin-only** transaction queries all linked payments, recomputes unreversed verified amounts, checks the stored aggregate and invoice total exactly, then marks it `paid` once with actor/time and audit entry. Admin cannot call this action successfully. No direct client invoice update is permitted.

Payment submissions from the invoice carry a browser-generated `operationId`. The trusted backend derives a stable payment document ID from the authenticated UID and this ID; an identical retry returns the existing payment without a second audit event. A changed retry is rejected. Legacy callers without an operation ID still receive auto IDs, so they do not have the same retry guarantee. Staff may correct only an **unverified** payment's mode/reference, with a mandatory reason. New online references are reserved permanently; an old reference stays reserved so historical evidence cannot be reused. The payment update, new reservation and `payment.mode_changed` audit event commit together. Verified records require the explicit reversal workflow. `listPaymentActivity` reads only server-scoped `referenceType == payment` events, with an additional `ownerUid` constraint for ordinary Users; the existing `auditLogs` composite indexes for `referenceType, at` and `referenceType, ownerUid, at` support these queries. Filters are applied to the authorized cursor stream. Older generic payment audit events without `ownerUid` remain readable to staff but do not appear in a User's activity list.

Reporting tables use server-side filters and cursors, with composite indexes in `firestore.indexes.json`; see [reporting query policy](./REPORTING.md). Existing financial and other operational UI queries still use some client-side filtering over authorized records. For large production datasets, replace those remaining scans with paginated server queries before scale.

For exactly-once behavior, use the source document's status transition plus deterministic operation/movement IDs as idempotency keys. Read all affected documents before writing in the transaction. Keep each operation within Firestore transaction and Security Rules limits; split or reject oversized orders rather than silently applying only part of them. Record ownership and line snapshots are assigned by backend logic, never accepted from a browser as authoritative. Google Drive permissions must be enforced in Drive; possession of a stored URL alone must not grant access.

## Why the backend boundary is necessary

Firestore Security Rules can check bounded document relationships with `getAfter()`, but large variable-length line arrays, stock arithmetic across many inventory documents, aggregate verified payments, idempotent status changes and authoritative audit logs cannot be reliably secured with arbitrary browser transactions alone. Rules have document-access call limits and cannot act as a general server-side aggregation engine. See [Firebase's atomic rules guidance](https://firebase.google.com/docs/firestore/manage-data/transactions) and [access-call limits](https://firebase.google.com/docs/firestore/security/rules-conditions).

Purchase, inventory, customer, order, special-product, invoice and payment operations use authenticated callable functions. Each operation verifies the Firebase ID token, **reads** the authoritative `users/{uid}` profile, enforces the exact role and writes balances/movements/audits through Admin SDK transactions. Cloud Functions for Firebase requires the Blaze plan and a billing account even if usage stays within no-cost quotas. The functions run locally in emulators but have not been deployed. If billing is unacceptable, keep browser writes denied and use an independently operated trusted process. A fully browser-only version cannot honestly promise these invariants.

## First Admin

In Firebase Console, create the first email/password Authentication user. Copy its UID, then create `users/{UID}` in Firestore with `role: "admin"`, `active: true`, and optional string `displayName`. Publish restrictive rules first. Sign in and verify access. Do not create a public Admin bootstrap route, use a client-supplied role, or put a service-account key in the web app. Restrict Firebase Console/IAM access to trusted maintainers; server SDK and Console access bypass Firestore Rules.

## User provisioning metadata

The saveUserProfileCall route now uses trusted Auth + Firestore provisioning, with fullName, email, displayName, role, active and server creation/update timestamps on users/{Auth UID}. Edits keep the UID. The new server-only userOperations/{operationId} stores actorUid, targetUid, create, desired fields, prior profile, status and updatedAt; userOperationLocks/{UID} stores operationId. Existing default-deny Rules prevent every client role from accessing these records. No passwords, reset codes or Auth tokens are stored. See USER_MANAGEMENT.md for partial-failure recovery. No migration or production update runs.
