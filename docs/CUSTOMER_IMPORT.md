# Bulk Customer Import

Active Admins can import previous-year customers from CSV, XLSX, or XLS on the Customers page. The import accepts the existing customer fields: name, phone/contact, area, address, optional ISO `YYYY-MM-DD` date of birth, optional Sabha Yes/No, and optional assigned User. Email is not part of the current customer schema and is not imported. Name, phone, area, and address are required. Phone values are strings; Excel users should format phone cells as Text before saving to preserve leading zeros. The browser uses the existing SheetJS loader for Excel and a local parser for CSV. No spreadsheet is uploaded for parsing or stored as a file.

The Admin selects a sheet, maps columns, chooses an optional default active User, and previews validation. Per-row assignment matches an active User by unique display name, full name, or email; spreadsheet UIDs are not accepted. Unassigned rows remain unassigned. Preview scans existing customer contacts and checks contact reservations from the server. Rows with existing contacts are skipped; duplicate rows can be skipped or block the import until the file is corrected. No existing customer is changed.

Each new customer uses the existing `saveCustomerDirect` transaction, which validates the fields, writes the customer and contact reservation, and creates its customer audit. The import supplies a SHA-256 job reference and source row number in the audit; Firestore Rules allow this import metadata only for Admin customer creation. IDs are deterministic from the normalized contact hash. Reopening or retrying the same file cannot create a second customer for that contact. A separate Admin-only summary audit records counts and the job reference without spreadsheet contents. Transactions are processed one row at a time, with progress updates every 25 rows and bounded reads during preview. Files are limited to 5 MB and 10,000 nonblank customer rows.

If an import stops, reopen the same file and preview again. Previously imported contacts appear as existing; failed rows can be retried. The final screen reports imported, existing, duplicate, invalid, and failed rows, including row-level reasons and assignments. Customer imports never write orders, invoices, payments, or historical references. No Cloud Functions deployment or billing change is required for this direct Firestore transaction path. The updated Firestore Rules must be published before live use; this task does not deploy them or change production data.
